# v0.3.0 — unreleased

This is an evolving release note, not a declaration that the v0.3.0 milestone is complete.
Remaining scope is tracked in the [roadmap](../roadmap.md).

## ARM64 native feature detection

- Linux detection reports MOPS, HBC and GCS from their kernel HWCAP bits.
- The strict v8.8/v8.9 compatibility requirements remain intact. Native automatic selection of
  these tiers is unavailable because NMI/THE cannot be safely observed; include a compatible
  fallback variant. The separate v9.x branch is unchanged.
- Collector fixtures and native ARM64 auxv checks have distinct evidence boundaries; a runner
  without those features does not qualify newer hardware. See the [ARM64 matrix](../architecture.md#8-arm64-aarch64-microarchitecture-matrix).

## Verified Linux installation

- A Bash bootstrap authenticates a pinned Cosign verifier and baseline native installer helper.
  No Go compiler, preinstalled Cosign, jq, Python or tar is required on the destination.
- Stable releases from v0.2.3 onward can be installed into user-owned or explicit system roots.
  Latest selection is frozen before authentication; downgrades require explicit intent.
- The CLI and both stubs are published as one complete generation, with a stable lock, ownership
  metadata and one atomic activation pointer. Manual and package-manager files are refused.
- Reinstall verifies existing bytes. Explicit repair handles owned corruption. Uninstall preserves
  modified entries, old generations and workload caches.
- The v0.3.0 CLI binds companion discovery to its physical running generation across native,
  memfd and cache execution, including activation races with identical payload bytes.
- Two native helper assets and their CycloneDX 1.7/SPDX 3.0.1 SBOMs extend the exact release
  checksum inventory to twelve payloads. The two fat product archives retain their three binaries.

The first public bootstrap requires published, authenticated v0.3.0 helper assets. Unsigned snapshot
validation does not satisfy that requirement. The tag release workflow qualifies exact signed draft
bytes on native amd64 and arm64 before the existing finalizer can publish a successful release.
Historical immutable assets are unchanged. No Homebrew tap, macOS support or automatic
generation pruning is introduced by the installer work.

Read [installation and migration](../installation.md), the [trust policy](../release-verification.md),
and the [ownership/discovery contract](../design/installation-discovery-contract.md).

## Explicit verified updates

- `microfat update --check` reports published stable availability using HTTPS metadata. Successful
  checks return 0; `--json` exposes `update_available` and the verification scope.
- `microfat update` authenticates the archive and atomically switches a complete installer-owned
  generation. Pinned downgrades require explicit consent; root updates require `--system`.
- Manual/Homebrew installs can check but cannot self-update. Stale running generations, concurrent
  activations, damaged ownership and corruption fail safely with actionable recovery guidance.
- Ordinary commands remain offline for update discovery. No generation pruning or adoption is added.

## Official Linux Homebrew tap

- The shared [EpicBlackWolfZ/homebrew-tap](https://github.com/EpicBlackWolfZ/homebrew-tap) repository
  supports a byte-preserving microfat cask for Linux amd64 and arm64.
- A pinned generator authenticates the public, immutable release's complete signed inventory,
  validates artifacts and SBOMs, and selects fixed hashes for both architecture archives.
- Native Homebrew qualification covers install, reinstall, upgrade, failed-checksum recovery,
  uninstall, sibling-stub discovery and package-manager ownership through memfd/cache dispatch.
- Tap-owned hourly automation proposes reviewed recipe PRs after both native jobs pass, using
  only its own GITHUB_TOKEN. Maintainers approve workflows and merge manually.

The first install command, `brew install --cask EpicBlackWolfZ/tap/microfat`, becomes available only
after v0.3.0 is public and its authenticated recipe PR is merged. No placeholder hashes or unsigned
snapshot recipes are published. See [installation](../installation.md#homebrew-linux-amd64-and-arm64)
and [tap maintenance](../homebrew.md). Issue #205 remains open until that first public cask is usable.

## Cache-first dispatch and resource policy

- Auto dispatch checks an existing cache entry read-only and executes its verified descriptor.
  Safe missing, corrupt or nonexecutable entries can use sealed memfd without changing the cache;
  unsafe owner/type/mode entries still fail closed.
- Extraction memory-budget refusal on an auto miss is terminal and leaves cache directories,
  permissions and entries untouched. A verified warm-cache hit does not extract the source payload.
- Explicit prewarm and cache materialization replace a safe nonexecutable entry with verified
  executable bytes. Read-only verification reports it unusable and leaves it intact.
- Native Go CPU adaptation can be selected independently of memory tuning. Explicit runtime
  environment settings keep precedence; source and native quota-change qualification remain distinct.
- CPU-only cgroup v1 quotas are detected without requiring a memory-controller mount.
- Cgroup membership lookup preserves trailing spaces, tabs and carriage returns. Direct v1 mounts retain
  their valid limits when an unrelated controller is unavailable. Finite zero v2 memory boundaries
  remain distinct from unlimited values and preserve independent CPU observations.
- For selected payloads, info reports the requested execution policy and prospective plans with
  computed tuning separate from inherited or injected application environment. Inspection leaves
  the cache untouched and does not execute the application.
- Full-launcher help/info and explicit all-tier or named-tier prewarm remain usable when no payload
  can be selected. Info reports the selection error without inventing a selected variant or runtime
  candidate; ordinary execution and host-selected transformations still require a compatible payload.

## Correctness and diagnostics

- Pack normalizes accepted amd64/arm64 aliases. Pack/build enforce Linux-only targets before payload
  processing or compilation. ELF validation checks payloads and custom launchers against machine/OSABI
  and available Go `GOOS` metadata; generic SysV ELF alone does not prove loader or libc compatibility.
- Automatic sibling and PATH launcher discovery uses the same canonical architecture for accepted
  aliases and casing. Explicit cache directories preserve legal relative whitespace-only names
  during cold materialization as well as warm verification.
- CLI trim, launcher transformation destinations and quoted manifest PGO filenames preserve
  intentional whitespace. Empty destinations are refused; whitespace-only filenames work.
  CLI trim also preserves a literal leading `=` after flag parsing; collisions use the exact name.
- Ordinary application arguments retain their bytes, including empty values, `--` and later
  reserved-looking flags. Lifecycle options are parsed only for transformation commands.
- In-place transformations recheck the hardlink count before publication. An alias added during
  staging causes the default refusal while preserving the source and alias bytes.
- Strict lifecycle transformations preserve the accepted sticky bit and verify all applied special
  mode bits before publication. Setuid/setgid inputs remain refused; strip removes special mode bits.
- Per-variant compression overrides follow canonical tier aliases. Explicit inline variant levels
  outrank inherited root levels, and equivalent accepted numeric zstd spellings select the same setting.
- Invalid UTF-8 application names are refused before publication; ordinary Unicode retains its bytes
  through supported binary and JSON output formats.
- Codec decompression enforces an exact zero-size declaration before destination writes and preserves
  underlying I/O errors for structured diagnostics. Direct dictionary training bounds oversized samples
  before encoding; normal pack sampling remains bounded.
- Payload/dictionary SHA-256 fields accept valid uppercase and mixed-case hexadecimal. Readers check
  the original index against its trailer hash, then normalize digests for verification and cache identity.
- Release archive readers verify every gzip member's CRC and size through EOF. Bounded zero padding
  remains accepted; malformed footers and nonzero trailing contents are refused before extraction succeeds.
- Release archive validation checks the shared dictionary's declared SHA-256 before decompression.
- Independent Linux release validation rejects foreign fat-index targets, ELF OSABI values and
  Go `GOOS` metadata in root and embedded executables before accepting the product archive.
- Benchmark configuration validates observer sampling limits and Go startup-compatible runtime
  controls before measured builds; matched controls use canonical effective observations.
- Baseline trial counts have a finite evidence budget and reject oversized requests before setup
  or allocation. Dedicated-host qualification requires governor and topology evidence for every
  selected target and generator CPU. Derived throughput density uses effective applied memory
  and CPU limits, including kernel-rounded memory ceilings.
- Warmup HTTP or transport failure stops a benchmark before steady-state load. Child identity,
  raw output and error evidence remain available; failed warmups cannot qualify performance comparisons.
- Benchmark cgroup setup failures attempt manager and parent cleanup independently while preserving
  the original failure status.
- Hosted benchmark teardown runs outside its recorded delegation before evidence upload. A protected
  receipt binds the run, attempt, owner and inode; PID file descriptors pin graceful termination, with
  scoped `cgroup.kill` for surviving workers. Native amd64/arm64 checks exercise orphaned manager and
  workload workers while unrelated processes and sibling groups survive. Measurement failures and
  incomplete evidence remain visible.

## Release acceptance boundaries

Source CI and unsigned snapshots establish source behavior and packaging. They do not establish
the identity or runtime behavior of an authenticated signed candidate, the first public helper/bootstrap
download, or an installable public Homebrew recipe. Those checks remain tracked by #203, #205 and #260.
Publication requires separate approval; the stable-tag workflows stage and qualify signed bytes and
can then publish automatically after the existing gates pass.
