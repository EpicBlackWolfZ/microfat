# v0.3.1

This patch release corrects installer argument handling, automatic dictionary selection and
launcher guidance, and refreshes dependencies and release tooling. Linux amd64 and arm64 retain
the same three-product archive layout and native installer helpers as v0.3.0.

## Installer and launcher corrections

- Semantic installer argument errors return exit status 2, consistently with the documented
  usage-error contract. Operational failures continue to return 1. This includes contradictory
  options and invalid installation roots. See [#361](https://github.com/EpicBlackWolfZ/microfat/issues/361).
- The v0.3.1 bootstrap authenticates the published v0.3.1 installer helper, independently of the
  requested product version. Use this new versioned bootstrap to receive the argument-handling
  fix. The immutable v0.3.0 bootstrap continues to use its v0.3.0
  helper, even when installing a newer product. See the [verification contract](../release-verification.md).
- Lifecycle staging permission failures give transformation-specific recovery guidance rather
  than suggesting unrelated cache recovery. See [#362](https://github.com/EpicBlackWolfZ/microfat/issues/362).
- `microfat pack --dict` skips automatic dictionary training when none of the effective variant
  codecs can use a dictionary. Per-variant codec overrides are included in that decision; explicit
  dictionary requests retain their validation. See [#363](https://github.com/EpicBlackWolfZ/microfat/issues/363).

## Documentation corrections

- Launcher flags and the minimal profile's capabilities match the implemented CLI. The minimal
  launcher retains execution and environment controls while omitting interactive meta-commands.
  See [#358](https://github.com/EpicBlackWolfZ/microfat/issues/358).
- The nonroot distroless trim example gives the intended user ownership of the deployment
  directory. See [#359](https://github.com/EpicBlackWolfZ/microfat/issues/359).
- Update usage errors keep stdout empty even with `--json`; diagnostics go to stderr with exit
  status 2. Successful JSON update results retain their existing schema.
  See [#360](https://github.com/EpicBlackWolfZ/microfat/issues/360).
- Lifecycle documentation describes the actual snapshot-before-lock ordering and the scope of
  the advisory inode lock. Independent readers and replacement inode writers are outside that
  advisory lock; byte identity, validation and atomic publication checks retain their own roles.
  See [#365](https://github.com/EpicBlackWolfZ/microfat/issues/365) and the
  [lifecycle contract](../lifecycle-modes.md).

## Dependencies and release tooling

- Builds target Go 1.27.3. The root `go.mod` supplies the Go version to workflows and generated
  fixtures; shared tool pins live in `.config/tool-versions.env`.
- Compression uses `github.com/klauspost/compress` v1.20.3. The benchmark workload is pinned to
  Fortio v1.76.0 with its verified source commit and public Go module checksum authentication.
- Task, GoReleaser, golangci-lint, vulnerability scanning, SBOM conversion, signing and Homebrew
  tooling use the refreshed, centrally maintained pins.
- Dependabot tracks Go modules, GitHub Actions and fixture container images. Renovate covers
  the remaining tools and updates coupled asset hashes, source commits and version references.
  See [dependency updates](../dependency-updates.md).
- The clean public installer fixture uses the pinned official Ubuntu 26.04 multi-platform image.
  Signal qualification keeps the reporter alive until its self-sent SIGTERM terminates it,
  preventing a normal-return race from producing false failures.
- QEMU cleanup qualification waits for the observed processes to be reaped after asynchronous
  PID-namespace teardown. The wait is bounded and retains failure and cleanup for surviving processes.
- Installer qualification includes the immediately preceding v0.3.0 release alongside the
  historical signing fixtures. Signed-candidate upgrades and downgrades retain authentication
  and restore the candidate after each historical transition.

## Compatibility and release acceptance

There is no new binary format, archive layout or supported operating-system target in this patch.
Format v2 remains the default, and legacy Format v1 reading remains supported until v0.4.0.
Existing installer ownership, generation activation, explicit downgrade and Homebrew management
policies are unchanged.

Release preparation and publication have separate gates. Source CI and unsigned snapshots do not
establish signed-candidate authentication or public availability. The tagged candidate must pass
native amd64/arm64 installer and runtime qualification, complete hosted benchmark evidence and
signed inventory verification before immutable publication. Hosted measurements are not
dedicated-hardware performance certification.

Public archive audits, clean native bootstrap qualification and the authenticated Homebrew recipe
retain their own evidence. Public Homebrew acceptance must use the reviewed, merged tap commit.
The record below identifies the source SHA, producer attempt, benchmark cohort and separate public
installer/tap stages. See the
[release order](../roadmap.md#reusable-release-order-and-exit) and
[release artifact guide](../release-artifacts.md).
